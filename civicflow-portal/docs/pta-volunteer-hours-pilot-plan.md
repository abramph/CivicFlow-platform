# Unestra for PTA — Volunteer Hours Controlled Pilot Plan

Companion to `docs/pta-volunteer-hours-rollout-runbook.md` (the general dark-launch procedure). This document is the **specific, concrete pilot design** — organization, scenarios, activation sequence, verification, rollback. Written during post-deployment monitoring on 2026-08-28, with the feature live in production but fully dormant (platform switch off, all six org flags off, zero rows in all nine new tables — see the deployment report for the exact verification).

**Nothing in this document authorizes any action.** It is planning only. Every stage below requires separate explicit authorization before execution, per the standing program constraint.

## Addendum (2026-08-30): a broader access gap than Stage C's Stripe question

Stage B execution surfaced a gap this document hadn't anticipated: Pine
Grove's non-billing-exempt status (§1 below, "relevant to Stage C") turned
out to block **all authenticated application access**, not just the
Stripe-test-mode question Stage C discusses — `src/lib/subscription-gate.ts`
denies every organization that is neither billing-exempt, mid-trial
(`trialEndsAt > now`), nor has an active `Subscription`, and Pine Grove
(created directly by the seed script, never through signup) has
`trialEndsAt = null`. Logging in as any Pine Grove officer redirected to
`/subscription-required` before Stage B's on-screen report verification
could even begin.

The resolution is `docs/internal-trial-grants.md` — a new
platform-admin-only service (`grantInternalOrganizationTrial()`) that gives
an eligible organization the same 30-day `trialEndsAt` window every
organization already gets for free at signup, with **no Stripe involvement
and no change to `billingExempt`**. This is a different mechanism than
Stage C's question below, which is specifically about unlocking
`stripe-connect.ts`'s test-mode checkout pathway — the internal trial
resolves general access; Stage C's `billingExempt` question, if it's ever
needed, remains a separate decision.

As of this addendum, the internal-trial service exists and is deployed but
**Pine Grove's trial has not been granted** — that remains a separate,
explicit action for a future authorization, per the standing program
constraint above.

## 3. Feature-flag activation sequence (planned, not executed)

Access now requires **three independent, server-enforced conditions together** — the pilot-allowlist hardening added a middle layer between the platform switch and each org's own capability flags:

1. **Platform switch** (`PTA_VOLUNTEER_HOURS_PLATFORM_ENABLED`) — global kill-switch, off means dark everywhere regardless of anything else.
2. **Pilot allowlist** (`PTA_VOLUNTEER_HOURS_ALLOWED_ORG_IDS`) — a comma-separated list of exact organization IDs; an org absent from this list is denied even with the platform on and its own flags already true. This is what makes the pilot *technically* restricted to Pine Grove, rather than merely relying on other organizations' administrators not choosing to enable their own settings.
3. **Organization capability flags** (`PtaProfile.ptaVolunteer*Enabled`) — unchanged from before, independent per capability.

Exact production changes Stage A would require, for reference at authorization time:

1. Set `PTA_VOLUNTEER_HOURS_PLATFORM_ENABLED=1` on the `civicflow-portal` DO app spec.
2. Set `PTA_VOLUNTEER_HOURS_ALLOWED_ORG_IDS=<PINE_GROVE_ORG_ID>` (single entry) on the same app spec — both env var changes can be applied in the same spec update, triggering one deployment, same blue/green behavior as the credential cutover and code deploy already verified this session. No code changes, no migration changes — env vars only.
3. `PATCH`/`PUT` `PtaProfile.ptaVolunteerRequirementsEnabled = true` for Pine Grove only, via the existing authenticated admin settings route (gated on both the platform switch and the allowlist per the hardening on `feature/pta-volunteer-hours-pilot-allowlist` — the settings panel becomes visible to a Pine Grove ORG_ADMIN/OWNER only once steps 1 and 2 are both live for that org).
4. Everything else (buyout, assessments, reports, notifications, native mobile) stays `false` for every org, Pine Grove included, until its own stage is separately authorized.

Any other PTA organization, including a reviewer account, remains denied throughout. Its administrator can't even see the settings panel to attempt turning `ptaVolunteerRequirementsEnabled` on in the first place (hidden unless the org is allowlisted), and a direct API write to that flag is separately rejected too — the allowlist is enforced at both the settings UI and the settings API, not just the capability guard.

**Stage A — Platform and requirements only**
- Enable platform switch + Pine Grove's `ptaVolunteerRequirementsEnabled` only.
- Create one `[PILOT]`-labeled requirement period.
- Assign requirements to the fictional families in §7 (Families 1, 2, 4, 5, 7 — the ones that don't need buyout/assessment machinery).
- Verify: family dashboard card renders correct totals; a second org (Riverside, still fully OFF) sees nothing; direct API calls from an unauthenticated or wrong-org session are rejected.

**Stage B — Reports**
- Enable `ptaVolunteerReportsEnabled` for Pine Grove only.
- Generate all seven reports on-screen and as `.xlsx`; verify against §9.

**Stage C — Buyout, nonfinancial simulation**
- Enable `ptaVolunteerBuyoutEnabled` for Pine Grove only.
- **Payment-testing approach, resolved**: `src/lib/payments/stripe-connect.ts`'s `startConnectOnboarding()`/`getStripeForMode()` already implements exactly the "properly isolated and supported test-mode pathway" the authorization calls for — but it activates Stripe **test** mode only for organizations with `billingExempt = true`. Pine Grove is currently `billingExempt = false`. Two options, both compatible with "do not conduct a real payment":
  - **(a) Recommended for the initial pilot, no prerequisite needed**: exercise `buildBuyoutQuote()` and the checkout-*preparation* step (rate resolution, eligibility, pending-purchase record creation) without ever calling `createVolunteerBuyoutCheckout()`'s Stripe call — this is explicitly what the authorization already permits ("server-side quote and checkout preparation tests without conducting a live charge") and requires zero configuration change.
  - **(b) Only if a true Stripe test-mode checkout walkthrough is wanted**: flip Pine Grove's `billingExempt` to `true` first — a small, separate, low-risk administrative change (identical in kind to what was already done for Harris PTA and the reviewer orgs) that would need its own explicit authorization, since it's a real production data change outside this pilot's flag set. Flagged as an **open decision** in the final report, not assumed.
- Offline-payment recording can be tested via the existing "record offline payment" admin path with a clearly-labeled fictional reference (e.g. `[PILOT] test check #0000`) — no Stripe involvement at all, no prerequisite.

**Stage D — Assessments, preview only**
- Enable `ptaVolunteerAssessmentsEnabled` for Pine Grove only.
- Generate one preview batch (Family 6 in §7), export the preview spreadsheet.
- **Never call the post-batch endpoint.** No `PtaVolunteerAssessmentCharge` row should exist at any point during the pilot.

**Stage E — Notifications**
- `ptaVolunteerNotificationsEnabled` stays **false** for the entire pilot. Template review happens exclusively through `previewVolunteerHoursNotification()`, sent to one designated internal test address, for all three notification types (deadline reminder, assessment posted, rate change).

**Stage F — Native mobile**
- Not touched. Deferred until Apple resolves the current submission, per standing constraint.

## 5. Rate-window test matrix

Fictional schedule (all dates relative to the `[PILOT]` period's own timezone, set explicitly rather than assumed):

| Window | Full buyout | Per-hour |
|---|---:|---:|
| Contract signing → Aug 15 | $250 | $12.50 |
| Aug 16 → Sep 30 | $300 | $15.00 |
| Oct 1 → Jan 31 | $400 | $20.00 |
| Final assessment | n/a | $25.00 |

Coverage required, each as its own test case against `resolveVolunteerBuyoutRate()`/`validateNoOverlap()`:
- Exact start boundary (inclusive) and exact end boundary (exclusive) of each window, in the organization's configured timezone specifically (not server-local/UTC — a real class of bug if the two diverge near midnight).
- A timestamp with no applicable window → clean rejection, not a silent fallback to any window.
- An attempt to create an overlapping window of the same rate type → rejected at write time (`validateNoOverlap`).
- A purchase made under window N, then window N is superseded by window N+1 → the purchase record's snapshotted rate must never change retroactively (historical snapshot integrity).
- Maximum buyout (`buyoutMaxPurchaseMinutes`) and minimum service (`buyoutMinServiceMinutes`) boundary enforcement.
- Full buyout vs. partial buyout paths both resolve to the correct rate type (`FULL_BUYOUT` vs `PER_HOUR`).
- Quote expiration — confirm a stale quote can't be replayed past its validity window.
- **Client-submitted price manipulation**: confirm the checkout endpoint never trusts a client-supplied amount — re-derive `buildBuyoutQuote()` server-side inside `createVolunteerBuyoutCheckout()` itself and compare, rejecting any mismatch. (This is already the documented design — `checkout/route.ts`'s own comment states the price is "always resolved fresh server-side" — the pilot should include one explicit test that tampers with the request body's `hoursElectedMinutes`/amount-adjacent fields and confirms the server-computed value wins.)

No production clock manipulation — every boundary test uses the requirement period's own configured `startAt`/`endAt` values relative to real current time, not a manipulated `Date.now()`.

## 6. Reporting verification plan

All seven reports (Family Summary, Detailed Activity, Event Hours, Compliance, Purchased-Hours & Financial, Individual Volunteer, Volunteer-Category), each checked for:

- On-screen JSON total = generated `.xlsx` total, exactly (the architecture guarantees this by construction — both consume the same `build*ReportData()` function — the pilot re-confirms it holds for real Pine Grove data, not just fixtures).
- Event + non-event verified minutes = total verified minutes.
- Pending minutes appear as their own column/figure, never folded into verified.
- Rejected minutes excluded from every positive total.
- Purchased and waived minutes never counted as service minutes anywhere they'd imply a family "volunteered" hours it didn't.
- `remainingMinutes` floors at zero in every report (matches the `max(0, ...)` convention already used everywhere else in the codebase).
- Financial report and columns restricted to FINANCE-equivalent permission; a STAFF-only viewer can generate the non-financial reports but not the financial one.
- A Pine Grove household can fetch only its own family-summary self-service report — never another Pine Grove family's, and never Riverside's.
- Riverside (fully OFF throughout) confirmed to 403/404 on every Pine Grove pilot report URL if guessed directly.
- Every exported cell passes through `sanitizeFormulaCell` — spot-check a family name/note field containing a leading `=`/`+`/`-`/`@` renders as literal text in the `.xlsx`, not a formula.
- Currency, percentage, date, and hour formatting spot-checked against the design doc's stated formats.

## 7. Rollback and cleanup plan

**Immediate stop** (any stage, any reason): flip `ptaVolunteerRequirementsEnabled` (and whichever later-stage flags are on) back to `false` for Pine Grove, then flip `PTA_VOLUNTEER_HOURS_PLATFORM_ENABLED` off at the platform level — the platform switch alone is sufficient to kill every code path everywhere, instantly, no restart needed (every guard re-checks on every request; the settings panel itself also re-hides immediately, per this session's hardening). Confirm the cron sweep's own flag re-check means it already skips a de-flagged org on its very next run — nothing further to stop, since nothing was ever scheduled during the pilot in the first place (Stage E never enables it).

**Preserve vs. remove fictional pilot records** — recommended: **retain them in Pine Grove, don't delete.** Reasoning:
- Pine Grove is already the codebase's permanent, dedicated fictional demo org (its own seed script re-runs are idempotent `upsert`s) — there's no "pristine state" to restore to that isn't already just "whatever fictional data is there."
- The ledger model (`PtaVolunteerLedgerEntry`) is deliberately append-only/immutable by design (mirrors financial-ledger conventions elsewhere in the codebase) — deleting rows out of an immutable ledger table, even fictional ones, works against the model's own invariants and isn't how the system expects to be operated. If the pilot data needs to stop being *visible*, that's what turning the flags off does; it doesn't require deleting rows.
- Keeping pilot data (clearly `[PILOT]`-labeled) makes a *second* pilot round, or a future demo/training walkthrough, cheaper and safer than re-creating fixtures from scratch.
- If truly not wanted long-term, the safe path is a **narrowly scoped, reviewed** deletion limited to `WHERE organizationId = '<PINE_GROVE_ORG_ID>' AND ...` the specific `[PILOT]`-prefixed period/household IDs created for this round — never a broad/unscoped statement, and only as a separate, explicitly authorized follow-up, not an automatic pilot-teardown step.

**Confirm other organizations unaffected**: re-run the same read-only checks used in the deployment report (all-org flag scan, all-nine-table row counts restricted to non-Pine-Grove `organizationId`s) after each stage and after teardown.

## 8. Observability & stop conditions

**Monitor during any active pilot stage:**
- `/api/health` and the platform-admin `/api/health/deep`.
- `doctl apps logs --type run`, filtered for the volunteer-hours route/table/guard/report keywords already used this session.
- HTTP status-code mix for `/api/labs/pta/volunteer-hours/*` (expect only Pine Grove's own authenticated traffic; anything from another org's session is itself a stop condition).
- `_prisma_migrations` (no new migrations expected mid-pilot), the nine feature tables' row counts (expected to grow only for Pine Grove).
- `PtaVolunteerNotificationLog` row count (expected to stay 0 — Stage E never enables real sends).
- `PtaVolunteerAssessmentCharge` row count (expected to stay 0 — Stage D is preview-only).
- Report-export job queue (`ReportExport` rows) and generated-file success/failure.
- Permission-denial log entries (`PtaError` 403s) — expected only from deliberate negative tests, not real users.
- Reviewer-account activity (Unestra Demo PTA, Unestra Demo Community) — expected to show *zero* volunteer-hours-flag exposure at any point; any nonzero reading is an immediate stop condition.

**Stop immediately and roll back if:**
- Any real (non-`[PILOT]`) family gains access to any volunteer-hours surface.
- Any real notification is sent (anything other than an explicit test-recipient preview).
- Any real payment is created (any Stripe charge outside an explicitly-authorized test-mode walkthrough).
- Any assessment is posted (any `PtaVolunteerAssessmentCharge` row appears).
- Either reviewer organization (App Store or Play Store) shows any volunteer-hours flag on, appears in the allowlist, or shows any related data.
- Any cross-organization read succeeds (Riverside, or any other org, sees Pine Grove pilot data, or vice versa).
- Any report's on-screen total diverges from its exported `.xlsx` total.
- Any direct/unauthenticated request to a volunteer-hours route succeeds while the relevant flag is off.
- Any organization other than Pine Grove appears able to use any volunteer-hours capability, regardless of its own database flags — this specifically means the allowlist itself has failed and is the highest-severity stop condition in this list.
- Mobile behavior changes in any way (any diff against the existing mobile-compatibility contract tests).
- Overall production stability degrades (new error-rate increase, latency increase, restart).
